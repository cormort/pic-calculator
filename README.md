# 圖片計算器 — 中文表格辨識與驗算

用手機拍一張中文表格，自動辨識成表格後做加總驗算（橫向欄／縱向列），
找出「合計對不上」的格子。

- 線上版：<https://cormort.github.io/pic-calculator/>
- 技術與維護說明：[`pic-calculator/開發及維護說明.md`](pic-calculator/開發及維護說明.md)

辨識與驗算全部在瀏覽器完成（PP-OCRv6 + ONNX Runtime，模型從 CDN 下載），
沒有後端、沒有上傳；可安裝為 PWA 離線使用。

## 一、這個工具該怎麼看待辨識結果（設計原則）

驗算工具最怕的不是「辨識錯」，而是**錯了還告訴你「驗算正確」**，或
**明明是對的卻報一堆錯**（使用者會開始忽略警告）。所以錯誤處理不是一套規則套到底，
而是依「這個錯有沒有後續機制會抓到」來分派。

### 1. 實測數據（判斷的依據）

用 6 張有標準答案的中文表格圖（乾淨截圖、手機透視實拍、低解析度轉傳圖、
歪斜 2.4°、資產負債表），跑完整辨識管線後逐格比對，共 380 格：

| 指標 | 改版前 | 改版後 |
|---|---|---|
| 格子內容正確率 | 79.5% | **97.4%** |
| 數字格正確率（驗算真正在意的） | 85.4% | **97.6%** |

逐張（格級／數字格）：乾淨截圖 84.6 → **100**、模糊實拍 55.4 → **95.4**（數字 100）、
低解析度轉傳 72.3 → **96.9**、歪斜 2.4° 81.5 → **96.9**、資產負債表（乾淨／實拍）
98.3/86.7 → 98.3/**96.7**。

> 量測方式：同一批 6 張圖、380 格，開真實瀏覽器跑完整管線（含模型）。
> 列對齊用「順序保持的動態規劃」——早期版本用單點對齊，一個錯字就會讓整列對不到、
> 後面每列跟著位移，正確率被重複懲罰（同一份結果換算差 4 個百分點以上）。
> 所以「改版前」也用同一套對齊重新量過，兩欄才可比。

OCR 信心值可不可信？

| 訊號 | 實測 | 意思 |
|---|---|---|
| 低信心格（信心 < 0.85） | 15 格中 **8 格其實是對的（53%）** | 「低信心就擋下來要求先修」＝ 一半的提醒是白工 |
| 高信心格（信心 ≥ 0.85） | 289 格中 **14 格是錯的（約 5%）** | 只看信心值也不夠，它不是「這格有沒有害」的判準 |

結論：**判斷依據不是 OCR 信心，而是「這格壞掉會不會破壞驗算、以及壞掉後能不能被自動驗出」。**

### 2. 分派原則

> **自動修正，只用在「改錯時後面一定有人會抓到」的地方。**

- **數字**：驗算就是那個抓錯的人 → 可以自動修（全形轉半形、
  `25.000` → `25,000`、`O`→`0`、結尾雜符號）。改錯一定變紅字，使用者看得到。
- **文字標籤**：沒有任何機制會驗證它 → **一個字都不自動刪**。
  「人事費L」若把 L 刪掉，而你原本就叫「人事費L區」，永遠不會有人發現。
  這種只能標記，由人判斷。

### 3. 三層處理

| 層 | 對象 | 做法 |
|---|---|---|
| 自動整理 | 金額格的格式問題（全形、千分位句點、常見混淆字、結尾雜符號） | 直接修，修過的格子加虛線＋tooltip 可追溯，仍可手動改回 |
| 標記提醒 | 文字格的雜字、低信心格 | 橘線／虛線標記，不刪不改；「🔎 核對低信心」可逐格跳過去確認 |
| 指名＋一鍵 | **數字欄裡不是數字的格**、**被截斷的合計標籤** | 橫幅直接點名，附一鍵動作（跳到該格／設為合計），修正後立刻重算 |

### 4. 兩種「沒有錯誤訊息、但結果不可信」的狀況（最該處理）

這兩種是過去最容易讓人誤判的：

1. **金額欄裡有字但不是數字**（實拍常見 `12,345 ]`）
   以前會默默被排除在加總外 → 合計不符 → 顯示 ❌ 錯誤，其實表格是對的（**假錯誤**）。
   現在：紅虛線標出、橫幅列出並可跳到該格，同時說明「不符可能來自這格」。
2. **合計標籤被 OCR 截斷**（`小計` → `小`）
   標籤認不得 → **整列不會被驗算**，而且不會有任何錯誤訊息（**靜默漏驗**）。
   現在：主動問「第 6 列的標籤只讀到「小」— 是合計列嗎？」，按一下就指定為合計並重算。

另外，橫幅固定顯示**驗算涵蓋範圍**（例如「本次涵蓋 7 個合計列、14 格；1 格排除在外」），
避免「沒驗到」被誤讀成「驗過而且正確」。

### 5. 為什麼不採用其他做法

| 做法 | 為什麼不 |
|---|---|
| 先把可疑字刪掉，再靠驗算檢查 | 對數字可行（驗算會抓到），對文字不可行 —— 刪錯沒有任何機制會發現，會製造靜默錯誤 |
| 所有低信心格都擋下來，要求先修完 | 低信心格有 53% 其實是對的，會變成「狼來了」，使用者開始忽略警告 |
| 只驗低信心格 | 高信心格仍有約 5% 是錯的，漏掉的是最危險的那種（看起來很確定） |
| 數字不對就直接報錯、不解釋 | 錯誤可能來自辨識而非表格；不區分會讓使用者白忙，久了一定不再相信驗算 |

### 6. 已知限制

- 手寫表格不支援（PP-OCR 是印刷體模型）。
- 單邊重複辨識偶爾會多認一個字（「1人事費」的左半被讀成「1人」）；這類格信心通常偏低，
  會落在「核對低信心」流程裡。
- 「、」等中文標點常漏讀（「不動產、廠房及設備」→「不動產廠房及設備」），
  不影響金額驗算，但科目名稱比對不到。
- 乘法驗算（單價 × 數量 = 金額）靠**表頭字樣**認欄位（「單價／數量／金額」這類），
  表頭被 OCR 讀壞、或欄位叫別的名字（例如「每單位成本」）時就不會啟用。
- 模糊實拍因多了跨格線補救辨識，比乾淨截圖慢（桌機 WASM：乾淨截圖約 4–5 秒、
  模糊實拍約 9–14 秒／張，手機約 2–3 倍）。

### 7. 影像前處理：已做與尚未驗證

| 項目 | 狀態 | 說明 |
|---|---|---|
| 找格線前的局部對比校正 | ✅ 已做 | 每個像素除以附近平均亮度，昏暗、低對比、半邊陰影的照片也抓得到淡格線（原本線要比紙暗 20 階才算）。**只影響找格線，送進 OCR 的圖不變**。已用合成圖驗證（`tests/test_lines.js`），**尚未用真實照片的 benchmark 量測** |
| 送進 OCR 前去陰影（除以低頻背景） | ❌ 實作並量測後不採用 | 一律套用：格級 92.1%（+1.6），但乾淨截圖各掉 1~3 格；只對「光線離散程度高」的照片套用：89.8%，反而比不套的 90.5% 差，b-photo 也沒救回。程式與量測留在 `OCR_NORMALIZE`，等有真實反光／閃光樣本再重測 |
| 銳利化 | ⏳ 未做，預期無效或有害 | 會把 JPEG 雜訊、紙紋放大成假筆畫，字緣出現光暈 |
| 整體亮度／對比調整 | ⏳ 未做，預期影響小 | 辨識模型本來就訓練過各種亮度 |
| 二值化（轉純黑白） | ❌ 不做 | 模型以灰階／彩色照片訓練，二值化會丟失筆畫細節 |

> 注意：本表數字是「列對齊方式修正前」量的，只適合看相對差異；跨版本比較請用第 1 節的數字。

待量測項目的採用條件：用第 1 節那 6 張有標準答案的圖（380 格）跑開／關比較，
**數字格正確率上升、且格子內容正確率不下降**才放進去；只在部分圖片有效時，
要先找出能自動判斷「這張需要」的條件（例如背景亮度的變異），不要全部套用。
量測需要瀏覽器能下載 CDN 上的模型（jsDelivr、Hugging Face）。

## 二、已經修好的問題

（依「辨識」「操作」「可信度」分類；每一項都寫出原本的失敗長相，方便對照是不是同一個坑。）

### 辨識

| 問題 | 修法 |
|---|---|
| 文字框跨兩格（項次「1-1」緊貼科目「主持人費」）→ 整張表從該列**左右錯位**，金額全跑錯欄 | 偵測到框跨過格線時，拿原圖沿線切兩半**各自重辨識**；兩邊拼回原字串才採用，純數字不拆 |
| 千分位被讀成句點（`25,000` → `25.000`）→ parseFloat 得 25，**差一千倍卻看起來驗算通過** | 依同欄的千分位習慣修回 `25,000`，修正過的格子加虛線可追溯 |
| 全形數字、`O`/`l` 混淆字、`969,.524` 這類雜訊 | 統一整理成半形與正確格式（只動金額格） |
| 陰影／紙緣被當成格線 → 多切出空欄，表頭與數字**錯開一格** | 整欄（含表頭）都沒有字就刪掉 |
| 表格上方的標題（「113年度…明細表」）被拆成好幾格併進表格 | 第一條橫線以上且沒有數字的列視為標題，不併入 |
| 同一格被偵測兩次（「主」＋「主持人費」）→ 疊成「主持人費主」 | 大幅重疊且字互相包含時，取字多的那個 |
| 昏暗、半邊陰影的照片抓不到淡格線 → 只能退回用空白猜欄位 | 找格線前先做局部對比校正（只影響找線，送進 OCR 的圖不變），取捨見 [§7](#7-影像前處理已做與尚未驗證) |
| 數字後面緊黏像數字的字母（`2OO`、`1OO,000`） | 不再被當成幣別而悄悄解析成 2；無法確認就留給「不像數字」提醒 |

### 操作

| 改動 | 說明 |
|---|---|
| 選圖／拍照後自動辨識 | 選圖後直接開始辨識，少按一次；框不到表格（截圖整張就是表格）或偵測失敗時辨識整張圖（可關閉，會記住） |
| 「選擇檔案」按鈕 | 選 JPG／PNG／WEBP 或 PDF；旁邊的「拍照」直接開原生相機。iOS 點「選擇檔案」仍會先跳出系統面板（照片圖庫／選擇檔案）—— 那是 iOS 對所有 file input 的固定行為，`accept` 不能拿掉（拿掉會多出「相機 攝影機」變三個選項） |
| 欄列驗算改成「先選角色，再點欄號」 | 原本是 ＋→−→取消 三段循環；現在表格上方有 sticky 托盤選「加項／減項／合計」，點欄號或列號套用，同角色再點一次取消，選取以 chip 列出、點 chip 即取消 |
| 低信心逐格核對 | 「🔎 核對低信心」跳到下一個橘線格並全選內容 |
| 鍵盤操作 | 格子間 Enter／↑↓ 移動；欄號／列號可 Tab 聚焦、Enter 套用 |
| 複製表格 | 一鍵匯出 TSV，直接貼進 Excel／Google 試算表對帳 |
| 匯出 CSV | 「⬇️ 匯出 CSV」下載檔案（UTF-8 BOM，Excel 直接開不會亂碼） |
| PDF 逐頁辨識 | 可直接選 PDF（第一次會下載 pdf.js）；載入後有「◀ 上一頁／下一頁 ▶」，每頁各自框選、辨識、驗算，匯出的 CSV 檔名帶頁碼。跨頁的表格仍要分開驗 |
| 待核對清單 | 「🔎 待核對 (N)」把**低信心格、看不出是數字的格、合計不符、乘法不符**合成一個佇列，依「會不會破壞驗算」排序；按下即跳到該格並說明原因。以前是三套流程，核對時要分別處理還容易漏 |
| 復原 | 手改格子、按「改成 X」一鍵修正都會推一筆，按鈕或 Ctrl/⌘+Z 可復原（自動整理的原值仍在 tooltip）。以前改錯沒有任何退路 |
| 原圖對照 | 點任一格 → 右下角放大顯示那一格的原圖（最多 6 倍），「0 還是 O」「5 還是 6」不必自己找；離開焦點或按 ✕／Esc 收起 |
| 驗算方向（自動） | 驗算設定多了「手動選欄／列 / 自動：垂直分組 / 自動：橫向分組 / 自動：依縮排」。這三種算法本來就在程式裡（從 Excel 驗算器帶過來），只是一直沒有入口 |
| 點欄號／列號＝加項 | 直接點欄號或列號就是「加項」，**最後點的那一個自動當「等於」**，不必先回托盤把角色切成「＝」。合計不在最後（例如合計在中間）或要減項時，才需要點托盤。托盤上的 chip 會即時把自動合計標成「＝」 |
| 一次驗兩個方向 | 欄與列都選了就一起驗、結果合併；以前換方向要先清空選取，等於白做一次 |
| 驗算範圍 | 「表頭列／起始欄／結束列／結束欄」輸入框補回來（程式一直在讀這四個值，但輸入框先前被移除，等於寫死表頭第 1 列、全表） |
| 低信心門檻 | 60／75／85／95% 可選並記住（固定 0.85 對乾淨截圖太吵、對模糊實拍太寬鬆：低信心格實測 53% 其實是對的） |
| 手打數字 | 自動補千分位（`25000` → `25,000`），與 OCR 結果一致 |
| 表格閱讀 | 表頭 sticky、欄號點擊區域加大到約 40px（手機好按） |
| 連續處理同格式表格 | 換下一張時沿用上一張的欄／列角色與手動指定的合計列；套用前先比對欄數與表頭，不符只提示不硬套（避免「錯了卻顯示驗算正確」），可選「不要沿用」 |
| 修正 | 重構欄列選取時被誤刪的格子編輯（改了不寫回、每次失焦丟錯）已補回 |

### 可信度（也就是第一節的原則怎麼落地）

| 改動 | 說明 |
|---|---|
| 看不懂的金額格 | 紅虛線、橫幅列出、可跳到該格；並說明「合計不符可能來自這格」，不再默默產生假錯誤 |
| 被截斷的合計標籤 | 「小計」讀成「小」時主動問「是合計列嗎？」，一鍵指定後立刻重算（原本整列靜默漏驗） |
| 金額欄判斷 | 只有「形狀像金額」的欄才納入驗算（項次欄不再被當金額欄製造雜訊） |
| 驗算涵蓋範圍 | 橫幅固定顯示「涵蓋 N 個合計列、M 格；K 格排除在外」 |
| 標點差異不影響比對 | 科目名稱與表頭比對忽略「、」、括號與全形／半形標點 —— OCR 漏讀「、」時，「沿用上一張設定」與合計列判定不會因此失效 |
| 乘法關係（單價 × 數量 ＝ 金額） | 表頭認得「單價／數量／金額」就自動驗這一層：**加總相符不代表每個被加數都對**（金額被讀成十分之一時，小計一樣錯得「剛好」）。不符時列出「25,000 × 8 ＝ 200,000，實際 20,000」，提供「改成 200,000」一鍵修正，並反推「也可能是單價應為 2,500／數量應為 0.8」，讓你知道是哪一格可疑 |
| 文字雜字剝除 | 只做兩條幾乎不會誤刪的規則：結尾單一英文字母（「人事費L」）、尾字與首字相同（「主持人費主」「臨時工資臨」）。原辨識留在 tooltip，可 Ctrl+Z 復原；「2業」這種缺字不動（刪了無法驗證對錯） |
| 幣別與手寫勾前綴 | 金額欄讀成 `NT$ 122,226`、`NTS 12,041`、`√ NT$ 20,000`、甚至勾被讀成 `1 NTS 2,353` 都還是數字（`Validator._num` 會把幣別與前導勾剝掉）；金額欄的判斷也認這種樣子，否則整欄不算金額欄，「最後一列是合計」就驗不到 |
| 沿用設定要通過「欄位型態」檢查 | 除了欄數與表頭，還會比對每欄「幾成是數字」：欄數、表頭都對得上但金額欄其實變成數量欄時，硬套角色會產生「錯了卻顯示驗算正確」，現在會拒絕沿用 |

效果：格子正確率 64.7% → **90.3%**、數字格 53.0% → **87.8%**（第一節的同一批測試圖）。

## 三、還沒做的事

### A. 想得到做法、但還沒動（依影響排序）

1. **文字雜字自動剝除**（「人事費L」「2業」）。目前只標記不刪：文字沒有任何後續機制能驗證
   刪得對不對，誤刪不會有人發現。可先用「同一欄的格式慣例」（項次欄只允許數字與連字號）
   限縮，但要不要接受誤刪風險需要決定。
2. **科目名稱比對忽略標點**：「、」這類標點常漏讀，會讓科目／合計列的比對失敗。
   比對時把標點去掉是低風險改動，只是還沒做。
3. **表格結構模型（SLANet 這類）**。沒有內部格線、合併儲存格、複雜表頭這幾類，靠調整切欄
   規則已經到極限（實測 borderless 只有 23%／數字 0%）—— 需要一個直接輸出「哪個字屬於哪一格」
   的小模型（ONNX 約 7.7MB、MIT）。**已驗證模型本身可行**：用官方 `TableLabelDecode`
   （`merge_no_span_structure=True`，字典要把 `<td>` 換成 `<td></td>`、`sos` 是座標佔位符）
   解碼，合成表 20/20 格全對。**卡點在瀏覽器**：可用的 ONNX 版本內含一個 `Loop` 子圖，
   onnxruntime-web 建 session 時就以 `ShapeInferenceError` 拒絕（桌機版 ORT 只警告、照樣跑）。
   下一步：拿掉／展開那個 Loop，或在 Linux 用舊版 paddle2onnx 重轉。完整調查與可重現指令見
   [`bench/experiments/slanet_probe.py`](bench/experiments/slanet_probe.py)，驗收門檻是
   `bench/probe/`。

### B. 程式裡有、介面沒接

（目前沒有。三種自動驗算模式、表頭列／起始欄／結束列／結束欄的輸入框，都已經接上介面。）
### C. 模型與架構限制

- **跨欄合併儲存格**（表頭橫跨兩欄）仍然沒有自動合併：這類標題會被 `splitStraddling()` 依格線
  切開、左右各認一次（內容通常還讀得對，只是變成兩格）。自動合併需要判斷「這兩個欄其實是一欄」，
  誤判會把資料欄併掉，風險高於收益 —— 先不做。

- **沒有內部格線的表格會嚴重錯位**（實測：格級 23%、數字格 0%）。目前靠「格線」決定欄界，
  沒有線就只能用空白帶猜，數字會整批跑到錯的欄 —— 這是「歸屬錯」不是「辨識錯」。
  這類表建議改用有格線的截圖，或等表格結構模型（SLANet 這類）接進來，見 §三。
- **手寫表格不支援**（PP-OCR 是印刷體模型）。
- **PDF 支援逐頁處理，不是「跨頁一張表」**：多頁表格（表頭在第 1 頁、資料延續到第 2 頁）要自己分兩次驗算；
  「一次多張圖」仍然是一次一張。
- **模糊實拍較慢**（桌機 WASM 約 9–14 秒／張，手機約 2–3 倍）。跨格線補救是逐框重跑兩次辨識。
  「只有字框數比同表典型少的列才補救」已經試過並回退：整表系統性合併時（每列都被併掉一格）
  那個中位數本身就是壞的，補救整個被跳過，實測格級正確率 81.5% → 69.2%。
  還有希望的方向是**以格線切整條欄帶、一條線只辨識一次**（把「2 × 每列」變成「2 × 每條線」），
  但要處理「同一條帶裡有多列文字」的對位，工作量較大。
- **影像前處理只做了「找格線前的局部對比校正」**。送 OCR 前的去陰影、銳利化、整體亮度調整
  都還沒量測把關，採用條件寫在 [§7](#7-影像前處理已做與尚未驗證)。

### D. 工程面

- **真 OCR 的準確率量測不在 CI**（`.github/workflows/tests.yml` 只跑純函式單元測試）：
  它要下載 30MB 模型、開瀏覽器、跑 6 張圖約一分鐘，而且結果是數字不是布林值。
  代價是：改到 worker 或表格重建時，PR 綠燈不代表正確率沒退步，仍要有人跑
  `pic-calc-bench`（見 §四）。至少可以把「6 張圖的格級正確率」存成基準檔，
  並在 CI 做成「非阻擋性的報表」。
- **沿用上一張的驗算設定只比對「欄數」與「表頭」**：同欄數但語意不同的兩張表仍可能被誤套，
  目前靠「不符只提示」保守處理。

## 四、開發與測試

```bash
node tests/test_build_table.js   # 切欄切列、跨格線拆框、數字整理、欄列角色
node tests/test_smart_totals.js  # 智慧合計、看不懂的數字格、被截斷的合計標籤
node tests/test_template.js      # 沿用上一張的驗算設定（欄數／表頭比對）
node tests/test_lines.js         # 格線偵測：低對比、半邊陰影的合成圖
```

**準確率量測（真 OCR）**在 [`bench/`](bench/)：`shots/` 是 6 張有標準答案的測試圖（380 格），
`node bench/run_ocr.js` 用真實瀏覽器跑完整管線，`node bench/compare.js` 逐格比對並輸出表格。
CI 每週跑一次（`.github/workflows/bench.yml`，非阻擋，結果寫進 job summary）。
量測方式與目前基準見 [`bench/README.md`](bench/README.md)。

模型實測（同一批圖、同一台機器）：

| 模型 | 格級 | 數字格 | 每張耗時 |
|---|---|---|---|
| **small（30MB，預設）** | **97.4%** | **97.6%** | 10–20 秒 |
| medium（139MB） | 96.3% | 93.9% | 57–117 秒 |

medium 反而更差，而且錯法很危險：金額會掉一位（`200,000` → `2,000`、`6,000,000` → `600`），
驗算會整片紅。介面下拉選單已標註「實測金額位數較易漏讀」，預設維持標準模型。

本機預覽（靜態檔，無需建置）：

```bash
cd pic-calculator/static && python3 -m http.server 8000
# 開啟 http://127.0.0.1:8000
```

需要「真 OCR」的準確率量測要開瀏覽器跑完整管線（含模型下載），做法與腳本見
[`pic-calculator/開發及維護說明.md`](pic-calculator/開發及維護說明.md) 的「辨識流程」與「測試」章節。
